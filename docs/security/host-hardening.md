# Host, TLS & Container Hardening Guide — Clothing ERP Suite

## 1. Network & TLS Hardening

### 1.1 HTTPS by Default
Production operations require modern TLS termination before any commercial or retailer data is entered.
- **Port 80 (HTTP)**: Unconditionally redirects all plain web traffic to HTTPS using HTTP status 301. Also provides an exception path for automated Let's Encrypt / ACME challenges (`/.well-known/acme-challenge/`).
- **Port 443 (HTTPS)**: Serves the web desk and REST APIs using TLS 1.2 and TLS 1.3 only. Legacy and insecure protocols (SSLv2, SSLv3, TLS 1.0, TLS 1.1) are rejected.
- **Modern Cipher Suites**:
  ```nginx
  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;
  ssl_prefer_server_ciphers off;
  ssl_session_timeout 1d;
  ssl_session_cache shared:ClothingSSL:10m;
  ssl_session_tickets off;
  ```

### 1.2 Certificate Deployment Modes

#### Mode A: Operator-Supplied Commercial / Enterprise Certificate
If an enterprise certificate is provided:
1. Place the certificate chain at `/etc/ssl/clothing-erp/cert.pem`.
2. Place the private key at `/etc/ssl/clothing-erp/key.pem`.
3. Set secure permissions:
   ```bash
   chmod 600 /etc/ssl/clothing-erp/key.pem
   chmod 644 /etc/ssl/clothing-erp/cert.pem
   ```
4. Reload Nginx: `nginx -s reload`

#### Mode B: Automated ACME / Let's Encrypt Mode
For domain-backed deployments:
1. Ensure DNS points to the public IP and ports 80 & 443 are reachable.
2. Run Certbot with the Nginx plugin:
   ```bash
   certbot --nginx -d erp.yourdomain.com
   ```
3. Certbot will configure certificate paths and set up auto-renewal via systemd timer.

#### Mode C: Initial Self-Signed Baseline
Upon initial installation inside an isolated container, `install-debian.sh` generates a local self-signed certificate if no custom certificate exists, allowing immediate HTTPS verification before production domain registration.

### 1.3 Security Headers & Content Security Policy (CSP)
Nginx applies strict HTTP response headers on every response:
- **Strict-Transport-Security (HSTS)**: `max-age=63072000; includeSubDomains; preload` forces browsers to interact exclusively over HTTPS.
- **X-Content-Type-Options**: `nosniff` prevents MIME-type confusion attacks.
- **X-Frame-Options**: `SAMEORIGIN` prevents clickjacking by disallowing framing across different origins.
- **Referrer-Policy**: `strict-origin-when-cross-origin` protects sensitive URL paths from leaking in external requests.
- **Permissions-Policy**: Restricts unnecessary browser hardware APIs (`camera=(), microphone=(), geolocation=(), payment=()`).
- **Content-Security-Policy (CSP)**:
  `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: /private/files/; font-src 'self' data:; connect-src 'self' wss: ws:; frame-ancestors 'self';`

### 1.4 Secure Cookies & Site Configuration
Frappe is configured to enforce cookie confidentiality:
```bash
bench --site clothing.local set-config host_name "https://erp.yourdomain.com"
bench --site clothing.local set-config session_cookie_secure 1
bench --site clothing.local set-config http_only_cookie 1
```

## 2. Initial Administrator Credential Management

### 2.1 Confidential Credential Generation
- The initial Administrator password is generated using cryptographically strong pseudo-random bytes (`openssl rand -hex 20`).
- Credentials are saved strictly to `/root/clothing-erp-credentials` with mode `0600` (readable only by root).
- Credentials are never transmitted over plaintext HTTP or displayed in standard process lists.

### 2.2 Forced Password Reset Procedure
On first sign-in, the administrator is required to update their credentials:
```bash
bench --site clothing.local set-config force_user_to_boot_to_password_reset 1
```

### 2.3 Credential File Deletion
Once the administrator signs in and establishes MFA and a permanent password:
```bash
# Securely erase the initial credential file
shred -u /root/clothing-erp-credentials || rm -f /root/clothing-erp-credentials
```

## 3. Systemd Service Sandboxing

All application systemd units (`clothing-erp-web`, `clothing-erp-socketio`, `clothing-erp-worker`, `clothing-erp-schedule`) generated by `deploy/render-services.py` run with defense-in-depth isolation:

```ini
[Service]
User=frappe
Group=frappe
WorkingDirectory=/home/frappe/frappe-bench
UMask=0027

# Security Sandboxing & Privilege Restrictions
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=read-only
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
RestrictNamespaces=yes
LockPersonality=yes
MemoryDenyWriteExecute=no
ReadWritePaths=/home/frappe/shared /home/frappe/frappe-bench/sites /run/clothing-erp /var/log
```

- **`NoNewPrivileges=yes`**: Prevents child processes from gaining elevated privileges via setuid/setgid binaries.
- **`ProtectSystem=strict`**: Mounts `/usr`, `/boot`, `/etc`, and system directories strictly read-only.
- **`ProtectHome=read-only`**: Prohibits unapproved writes across `/home`, allowing reads of application code while isolating site data.
- **`PrivateTmp=yes`**: Allocates an isolated `/tmp` namespace per service, preventing cross-service temporary file leakage.
- **`ReadWritePaths`**: Restricts filesystem writes explicitly to the shared storage root, sites directory, socket runtime directory, and logs.

## 4. MariaDB & Redis Local Isolation

### 4.1 MariaDB Hardening (`/etc/mysql/mariadb.conf.d/60-clothing-erp.cnf`)
```ini
[mysqld]
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci
bind-address=127.0.0.1
innodb-snapshot-isolation=OFF
skip-name-resolve
```
- Bound exclusively to loopback (`127.0.0.1`); external TCP connections to port 3306 are blocked.
- MariaDB socket permissions restricted to `mysql:mysql` (mode `0750`).

### 4.2 Redis Hardening
- Bound strictly to `127.0.0.1` and local Unix sockets (`/run/clothing-erp/`).
- Protected mode enabled by default; direct external access to ports 6379, 11000, 12000, and 13000 is blocked.

## 5. Proxmox LXC Container & Firewall Rules

### 5.1 Unprivileged Container Isolation
- **Unprivileged Mode (`--unprivileged 1`)**: Container root (UID 0) maps to an unprivileged subuid (UID 100000+) on the Proxmox host. Kernel exploits within the container do not grant root on the host.
- **No Unnecessary Nesting**: Docker-in-LXC nesting (`features: nesting=0`) is disabled unless explicitly verified in isolated staging environments.

### 5.2 Ingress Firewall Rules (`deploy/proxmox/clothing-erp.fw`)
Deploy to `/etc/pve/firewall/<CTID>.fw`:
- **Default Policy**: `policy_in: DROP`, `policy_out: ACCEPT`.
- **Inbound Allowed**: Port 443 (HTTPS), Port 80 (HTTP 301 Redirect / ACME).
- **Inbound Blocked**: Ports 3306 (MariaDB), 6379 (Redis), 8000 (Gunicorn), 9000 (Socket.IO).

## 7. Maintenance, Log Rotation & Security Updates

### 7.1 Log Rotation (`/etc/logrotate.d/clothing-erp`)
```text
/var/log/clothing-erp-*.log /home/frappe/frappe-bench/logs/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 frappe frappe
    sharedscripts
}
```

### 7.2 Security Updates Procedure
1. Run automated Debian security patch sweeps:
   ```bash
   apt-get update && apt-get upgrade -y --only-upgrade
   ```
2. Inspect MariaDB, Redis, and Nginx status post-patch.
3. Test suite application health endpoints:
   ```bash
   curl -kfsS https://127.0.0.1/api/method/ping
   ```
